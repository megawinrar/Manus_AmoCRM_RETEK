# Архитектура и бизнес-логика системы RETEK amoCRM

> **Дата:** 10 Июня 2026
> **Версия:** 1.0 (PATCH18)
> **Репозиторий:** [Manus_AmoCRM_RETEK](https://github.com/megawinrar/Manus_AmoCRM_RETEK)

Этот документ описывает полную бизнес-логику, архитектуру и процессы микросервиса автоматизации тендеров RETEK. Система предназначена для автоматического сбора, распознавания, дедупликации и маршрутизации тендерных заявок в amoCRM.

---

## 1. Обзор системы

Микросервис написан на Python (FastAPI + APScheduler) и выполняет роль связующего звена между Яндекс.Диском (где появляются новые тендеры) и amoCRM (где ведётся работа менеджеров).

### 1.1. Ключевые компоненты
1. **API Сервер (FastAPI):** Принимает вебхуки от amoCRM (создание сделок, добавление примечаний).
2. **Фоновые задачи (APScheduler):** Регулярно опрашивают Яндекс.Диск, контролируют дедлайны, архивируют старые сделки.
3. **Модуль распознавания (`extract_and_classify.py`):** Извлекает текст из PDF/DOCX/XLSX, использует regex и OCR для парсинга полей тендера.
4. **Модуль дедупликации (`deduplication.py`):** Проверяет новые тендеры на совпадение с существующими по хешу файлов и fuzzy-логике (ИНН, НМЦ).
5. **amoCRM Client (`amo_client.py`):** Обертка над API amoCRM с поддержкой rate-limit и автоматических повторов (retries).

## 3. Бизнес-логика маршрутизации

При создании новой сделки система определяет её статус и ответственного на основе двух параметров: **Приоритет** (Р1-Р4) и **Тип ситуации** (СОЗ / Реальные торги / Неясно).

| Приоритет | Тип ситуации | Целевой статус | Ответственный |
|---|---|---|---|
| Р1 / Р2 / Р3 | СОЗ | 3. СОЗ — звонок | Сотрудник 2 |
| Р1 / Р2 / Р3 | Запрос котировок / реальные торги | 5. Передано в закупку | Сотрудник 3 |
| Р1 / Р2 / Р3 | Неясно | 2. Проверка Сотрудника 2 | Сотрудник 2 |
| Р4 (любой) | Любая | 11. К архивированию | Сотрудник 2 |
| Любой | Не наш ассортимент | 11. К архивированию | Сотрудник 2 |

### 3.1. Приоритеты и цветовые теги
Приоритет влияет не только на маршрутизацию, но и на визуальное отображение сделки:
- **Р1_СРОЧНО** (Красный тег) — Дедлайн подачи ≤ 48 часов. Сделка автоматически переименовывается в `[P1] СРОЧНО — Заказчик — DD.MM`.
- **Р2_БыстрыеДеньги** (Жёлтый тег) — Стандартный приоритет для быстрых сделок. Название: `[P2] — Заказчик — DD.MM`.
- **Р3_СредниеДеньги** (Зелёный тег) — Низкий приоритет.
- **Р4_Наблюдаем** (Серый тег) — Мусор, дубли или не наш ассортимент.

*Примечание: Если система определяет приоритет Р2, но до дедлайна осталось менее 48 часов, сделка автоматически эскалируется до Р1.*

## 4. Жизненный цикл тендера

Система поддерживает два основных способа получения тендеров: автоматический парсинг папки на Яндекс.Диске и ручной запуск через чат amoCRM.

### 4.1. Автоматический парсинг (cron_yadisk.py)
Каждые 30 минут (`:30` каждого часа) запускается задача опроса Яндекс.Диска:
1. Система проверяет папку `/ТОРГИ/`.
2. Находит новые файлы и ZIP-архивы.
3. Распаковывает архивы во временную директорию.
4. Вычисляет SHA-256 хеши всех файлов.
5. Проверяет наличие дублей в локальной SQLite базе (`processed_tenders.db`).
6. Если дубль точный (все файлы уже были) — сделка игнорируется.
7. Если тендер новый — запускается `extract_and_classify.py`.
8. Создаётся новая сделка в amoCRM с заполненными полями, тегами и прикреплёнными файлами (в виде ссылки).
9. Срабатывает Post-create hook: добавляется статусная заметка и ставится задача ответственному сотруднику.

### 4.2. Ручной запуск (Действие 3 — webhook_handler.py)
Менеджер может запустить распознавание тендера прямо из карточки amoCRM:
1. Менеджер создаёт сделку вручную.
2. Вставляет в примечание (чат) ссылку на папку Яндекс.Диска (например, `https://yadi.sk/d/...` или `disk:/ТОРГИ/...`).
3. Добавляет команду (опционально): "распознай", "парсинг", "тендер".
4. amoCRM отправляет webhook на сервер.
5. Сервер перехватывает ссылку, скачивает файлы через public API Яндекс.Диска.
6. Запускается `extract_and_classify.py`.
7. Сервер обновляет карточку сделки (PATCH запрос) — заполняет НМЦ, Заказчика, Направление, Приоритет, Дедлайн.
8. Сервер переименовывает сделку по стандарту `[P{n}] — Заказчик — DD.MM`.
9. Сервер отправляет отчёт в чат сделки.

## 5. Дедупликация и обогащение

Модуль `deduplication.py` реализует 3 уровня проверки:

1. **Точный дубль (File Hash Match):** Если 100% файлов нового тендера совпадают по SHA-256 с уже обработанным тендером — новый тендер полностью игнорируется (СТОП).
2. **Обогащение (Partial Hash Match):** Если часть файлов совпадает (например, 2 из 5), а остальные новые — система находит старую сделку в amoCRM, добавляет в неё новые файлы (в виде примечания) и ставит задачу "Поступили новые файлы/разъяснения". Новая сделка не создаётся.
3. **Fuzzy Match (ИНН + НМЦ):** Если файлы абсолютно новые, но ИНН Заказчика и НМЦ (с погрешностью 1%) совпадают с существующей сделкой за последние 30 дней — создаётся новая сделка, но с тегом `ВОЗМОЖНЫЙ_ДУБЛЬ` и предупреждением для менеджера.

## 6. Модуль распознавания (extract_and_classify.py)

Вместо медленного и дорогого вызова LLM для каждого файла, система использует гибридный подход:
1. **Экстракция текста:** `pdftotext` для PDF, `python-docx` для Word, `openpyxl` для Excel.
2. **Детекция сканов:** Если PDF содержит менее 100 символов на страницу, он признаётся сканом.
3. **OCR Fallback:** Для сканов используется `tesseract` + `pdf2image`.
4. **Regex Парсинг:** Извлечение ИНН, НМЦ (поиск сумм рядом с "НМЦК", "Начальная цена"), дедлайнов (поиск дат рядом с "окончани", "подач").
5. **Классификация направлений:** Поиск ключевых слов (например, "фрез", "сверл" → CARBIDE-STANDARD).

Скорость обработки: ~2-3 секунды на тендер из 5-10 файлов (без OCR).

## 7. Фоновые задачи (Cron Jobs)

Система поддерживает порядок в CRM через планировщик APScheduler:

1. **Ежечасный контроль (`cron_hourly.py`):**
   - Проверяет все активные сделки.
   - Если дедлайн подачи ≤ 48 часов, а приоритет ниже Р1 — эскалирует сделку до Р1 (меняет тег, переименовывает, ставит срочную задачу).
2. **Ночная архивация (`cron_daily.py`):**
   - В 02:00 собирает все сделки в статусе «11. К архивированию».
   - Проверяет заполненность обязательных полей (Причина закрытия, Архивное назначение).
   - Если поля заполнены — переносит сделку в соответствующую архивную воронку.
   - Если не заполнены — ставит задачу менеджеру "Заполнить поля для архивации".
3. **Еженедельный контроль зависших (`cron_weekly.py`):**
   - В понедельник утром ищет сделки, которые не меняли статус более 7 дней.
   - Ставит задачу руководителю.
4. **Резервное копирование (`cron_backup.py`):**
   - Ежедневно делает полный дамп всех сделок и задач в JSON.
   - Сохраняет локально и загружает на Яндекс.Диск в папку `/ТОРГИ/_BACKUP/`.

## 8. Инфраструктура и Деплой

Система развёрнута на виртуальной машине Yandex Cloud (Ubuntu 22.04).

- **Контейнеризация:** Docker + Docker Compose.
- **Сервисы:**
  - `app` — FastAPI приложение + cron (Python 3.11).
  - `nginx` — Reverse proxy для приёма вебхуков на порту 80.
  - `certbot` — Заготовка для SSL (пока используется HTTP по IP).
- **База данных:** SQLite (`data/processed_tenders.db`) монтируется как Docker Volume.
- **Логи:** Монтируются в `/opt/Manus_AmoCRM_RETEK/data/llm_logs/`.

Команда для обновления и перезапуска:
```bash
docker compose -f deploy/docker-compose.yml build app
docker compose -f deploy/docker-compose.yml up -d app
```

## 12. Webhook API

Сервер принимает POST-запросы от amoCRM на endpoint `/webhook`.

### 12.1. Формат входящих данных
amoCRM отправляет данные в формате `application/x-www-form-urlencoded`. Ключи имеют вложенную структуру:
```
leads[add][0][id]=12345
leads[add][0][name]=Тендер
leads[update][0][id]=12345
leads[update][0][status_id]=86357690
notes[add][0][element_id]=12345
notes[add][0][text]=Текст примечания
```

### 12.2. Обработка событий
| Событие | Ключ | Действие |
|---|---|---|
| Создание сделки | `leads[add]` | Логирование (будущее: автозаполнение) |
| Обновление сделки | `leads[update]` | Проверка смены статуса → создание задачи |
| Добавление примечания | `notes[add]` | Поиск ссылки на Я.Диск → Действие 3 |

### 12.3. Защита от бесконечного цикла
Когда бот пишет заметку в карточку, amoCRM отправляет webhook обратно. Для предотвращения бесконечного цикла:
- Фильтр по префиксам: заметки начинающиеся с эмодзи бота (🤖, ✅, ❌, ⚠️) игнорируются.
- Фильтр по маркерам: заметки содержащие "найдена ссылка на яндекс.диск", "скачано файлов", "распознавание завершено" игнорируются.

## 13. Действие 3 — Полный пайплайн

Файл: `src/microservice/action3_handler.py`

### 13.1. Триггеры
- Ссылка на Яндекс.Диск в тексте примечания: `https://yadi.sk/d/...`, `https://disk.yandex.ru/d/...`, `disk:/ТОРГИ/...`
- Ключевые слова: "распознай", "парсинг", "parse", "extract", "тендер"

### 13.2. Пайплайн обработки
```
1. Парсинг ссылки из текста примечания
2. Скачивание файлов через Яндекс.Диск Public API
3. Распаковка ZIP-архивов
4. extract_file() для каждого файла (PDF/DOCX/XLSX)
5. parse_tender_fields() — regex-парсинг полей
6. validate_and_ocr_fallback() — OCR для сканов
7. resolve_routing(priority, situation) — определение статуса
8. PATCH /leads/{id} — обновление карточки в amoCRM
9. Переименование сделки: [P{n}] — Заказчик — DD.MM
10. Отчёт в чат карточки
```

### 13.3. Заполняемые поля
- `customer` — Заказчик (название организации)
- `nmc` — НМЦ (числовое значение в рублях)
- `direction` — Направление (CARBIDE-STANDARD / HSS-GOST / SPEC-DRAWING / DIAMOND)
- `priority` — Приоритет (Р1 / Р2 / Р3 / Р4)
- `situation_type` — Тип ситуации (СОЗ / Реальные торги / Неясно)
- `procedure_number` — Номер закупки
- `deadline` — Дедлайн подачи

## 14. LLM-классификатор (llm_classifier.py)

Система использует Яндекс GPT (через OpenAI-compatible endpoint) для трёх типов задач:

### 14.1. Действие 1 — Классификация тендера
- **Вход:** Текст тендера (из extract_and_classify).
- **Выход:** JSON с полями: direction, priority, situation_type, confidence.
- **Контекст:** RAG-система подбирает релевантные чанки из `CONTEXT_FULL.md`.
- **Режим:** `training` — логирует результат, но НЕ применяет к сделке (для обкатки).

### 14.2. Действие 2 — Архивное назначение
- **Вход:** Данные сделки из статуса «11. К архивированию».
- **Выход:** Рекомендация по архивной воронке и статусу.
- **Запуск:** Ночной cron (02:00).

### 14.3. Действие 3 — Распознавание из чата
- **Вход:** Ссылка на папку с файлами.
- **Выход:** Заполненные поля карточки.
- **Запуск:** Webhook (примечание в карточке).

## 15. RAG-система

Для повышения качества классификации используется RAG (Retrieval-Augmented Generation):
- **Индексация:** `rag_indexer.py` разбивает документы на чанки (250 токенов, overlap 75), генерирует embeddings через Яндекс Embeddings API (256 dim), сохраняет в ChromaDB.
- **Поиск:** `rag_search.py` выполняет семантический поиск с keyword boost и query expansion, возвращает top-10 релевантных чанков.
- **Стоимость:** ~1.81₽ за индексацию тендера, ~0.001₽ за поисковый запрос.

## 18. Известные ограничения

1. **Нет SSL:** Webhook работает по HTTP (нет домена для Let's Encrypt). amoCRM допускает HTTP для вебхуков.
2. **Один процесс:** FastAPI + APScheduler в одном контейнере. При высокой нагрузке (>50 тендеров/час) может потребоваться разделение.
3. **SQLite:** Не поддерживает конкурентную запись. При масштабировании — перейти на PostgreSQL.
4. **amoCRM Rate Limit:** 7 запросов/сек. Система соблюдает лимит через `_wait_rate_limit()` в `amo_client.py`.
5. **Яндекс.Диск Public API:** Для скачивания файлов по публичной ссылке — лимит 50 запросов/мин.
6. **OCR:** Tesseract работает медленно (~5 сек/страница). Используется только для сканированных PDF.
